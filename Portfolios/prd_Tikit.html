01 · PROBLEM

카카오톡으로 뿌려지는 초대는
대체로 셋 중 하나였습니다.

사적인 이벤트를 여는 사람은 많은데, "모이게 만드는 초대장"의 비주얼과 참석 관리를 한 번에 해결해주는 서비스가 한국 시장에 없었습니다.

Option 1

구글폼 · 네이버폼

투박하고 정보만 받습니다. "간다 / 안 간다"를 묻는 폼이 이벤트의 첫인상이 됩니다.

Option 2

카카오톡 단톡방

참석 의사를 사람 손으로 집계해야 합니다. 이미지나 디자인은 전혀 남지 않고 기록도 없습니다.

Option 3

Partiful · Paperless Post

감성은 좋지만 카카오톡 OG 미리보기와 한국어 UX가 애초에 맞지 않습니다.

INSIGHT

카카오톡으로 공유되는 링크는 OG 이미지 한 장이 첫인상을 좌우합니다.
그러면 OG 이미지 자체가 초대장이 되어야 합니다.

02 · SOLUTION

링크 한 줄로 초대가
감상이 되는 경험.

제품을 만들기 전에 다섯 가지 설계 원칙을 먼저 정했습니다. 이후 모든 기능·품질·보안 의사결정은 이 원칙에서 나왔습니다.

01

티켓은 장식이 아니라 약속입니다

초대장은 실물 티켓 카드처럼 보여야 합니다. 카드 앞면, 뒷면, 그라디언트, OG 이미지 모두 같은 티켓 언어로 말합니다. 이름에서 뽑아낸 그라디언트가 클라이언트와 서버 어디에서 그려지든 똑같이 나오게 설계했습니다.

02

로그인 없이도 참석할 수 있습니다

참석자에게 가입 장벽을 두지 않습니다. 이름 한 줄, 한 번의 탭으로 RSVP가 끝나야 합니다. 익명 참석자도 안전하게 집계될 수 있도록 인증 계층을 통일했습니다.

03

PC와 모바일 어디서 열어도 자연스럽게

카카오톡에서 탭해 모바일로 들어오는 동선과, 데스크톱에서 공유받아 여는 동선 모두 티켓 경험이 일관되게 유지되도록 크로스 플랫폼 레이아웃을 설계했습니다.

04

카카오톡 미리보기가 첫 화면입니다

공유 링크의 OG 이미지가 곧 이벤트의 얼굴입니다. 서버에서 이벤트마다 고유한 티켓 이미지를 그때그때 생성해 카카오톡 미리보기에 바로 띄웁니다.

05

기본은 안전하게

RSVP나 외부 API 요청이 반드시 서버를 거치도록 설계했고, 비밀번호 해싱 같은 기본 관행을 따랐습니다. 혼자 작업하는 만큼 AI 도구로 코드를 반복 점검받아 놓칠 수 있는 부분을 줄였습니다.

03 · UX DETAILS

디테일이 서비스를 완성합니다.

기능 목록보다 더 중요한 건 "이 초대장이 카카오톡에서 어떻게 보이는가" 같은 미세한 경험입니다. 아래는 서비스 품질을 결정지은 여섯 가지 디테일입니다.

한 장의 티켓이 끝까지 이어지는 구조

생성 단계에서 본 카드 = 카카오톡에 뜨는 OG 이미지 = 상세 페이지의 티켓이 모두 같은 그림입니다. 앞면은 포스터 감성, 뒷면은 행사 상세. "FLIP" 펄스 애니메이션이 처음 온 사람에게 카드를 뒤집어보도록 자연스럽게 유도합니다.

OG 이미지가 곧 제품의 얼굴

카카오톡에서 링크를 탭하기 전부터, 사용자는 이미 이벤트의 티켓 카드를 한 번 본 상태입니다. 이미지 있는 이벤트 / 없는 이벤트는 레이아웃을 분기해서 각각 다르게 렌더합니다.

바이럴 루프 설계

참석자 페이지 하단에 "나도 초대장 만들기 →" 작은 CTA. 호스트 본인에게는 노출되지 않습니다. "이 초대장 예쁘네 → 나도 만들어볼까"까지 가는 심리 동선을 최대한 짧게 유지합니다.

카카오톡 중복 메시지 방지

카카오 공유 시 제목·설명을 일부러 비웠습니다. 그렇지 않으면 사용자가 친구에게 보낸 메시지 텍스트와 링크 미리보기 텍스트가 중복으로 떠서 스팸처럼 보입니다.

신호등 참석자 UI

갈래요 / 미정 / 못가요를 신호등 컬러(초록·노랑·빨강)로 시각화했습니다. 호스트가 한눈에 인원을 파악할 수 있고, "호스트 / 참석" 뱃지로 권한도 명확히 표시됩니다.

휴지통 (soft-delete)

이벤트 삭제는 바로 지우는 게 아니라 휴지통으로 먼저 보냅니다. 소유자는 다시 복구할 수 있고, 실수 삭제와 관리자 감사 두 가지를 모두 대응합니다.

04 · FEATURES

여섯 개의 기능 축.

제품을 여섯 개의 축으로 분해해 각자 독립적으로 작동하면서도, 티켓 메타포로 연결되도록 설계했습니다.

4단계 생성 위저드

테마 → 정보 → 장소 → 이미지·공개설정. 6 + 15종의 이름 시드 그라디언트 테마, Google Places 검색, 드래그 기반 이미지 위치 편집기까지.

정원 안 꼬이는 RSVP

여러 명이 동시에 참석을 눌러도 정원이 꼬이지 않습니다. 서버가 한 번에 한 건씩만 처리해서 중복·초과를 원천 차단합니다.

서버 렌더 OG 이미지

이벤트마다 고유한 600×800 티켓 이미지를 서버에서 그려 카카오톡 미리보기에 바로 띄웁니다. 클라이언트 티켓과 완전히 같은 그라디언트로.

공유 바텀시트

카카오톡 공유 + 티켓 카드 이미지 저장 + 링크 복사. 세 가지 공유 경로를 바텀시트 하나에 담았습니다. 인스타 스토리용 캡처도 한 번에.

Google + Kakao + 익명 로그인

세 가지 인증 경로를 제공하고, 같은 이메일이면 Google과 Kakao 계정을 자동으로 연결합니다. 익명 로그인으로 비로그인 RSVP도 안전하게 집계.

마이 이벤트 3뷰

리스트 · 덱(스와이프) · 캘린더 세 가지 뷰를 제공합니다. 호스트·참석 뱃지로 권한을 구분하고, 검색·정렬·필터도 한곳에 모았습니다.

05 · DECISIONS

주요 의사결정과 이유.

"왜 이렇게 만들었는가"가 코드보다 중요합니다. 기술 세부는 짧게, 결정의 이유는 분명하게 정리했습니다.

01

RSVP는 서버가 한 번에 한 건씩만 처리

문제 · 여러 명이 동시에 참석 버튼을 누르면 정원이 꼬이거나 같은 사람이 두 번 등록될 수 있음.
선택 · 저장은 반드시 서버를 거치게 하고, RSVP 경로를 한 곳으로 모음.
효과 · 정원·중복을 다루는 흐름이 한 군데로 모여 점검 범위가 줄어듦.

02

DB 문서와 UI 사이에 변환 함수 한 겹

문제 · 개발 초반 필드명과 지금 필드명이 달라서, 예전에 만든 이벤트가 UI에 빈칸으로 뜨는 버그가 있었음.
선택 · DB에서 가져온 원본을 UI가 절대 그대로 쓰지 못하게 하고, 가운데에 "변환 함수 한 겹"을 두어 예전 필드와 지금 필드를 한곳에서 맞춰줌.
효과 · 새 필드를 추가해도 한 곳만 고치면 돼서 같은 종류의 버그가 구조적으로 재발하지 않음.

03

티켓 그라디언트는 "이름에서 뽑아냄"

문제 · 티켓 카드(웹 화면)와 OG 이미지(카카오톡 미리보기)가 서로 다른 그라디언트를 그리면 티켓 일관성이 무너짐.
선택 · 이벤트 이름을 시드로 사용하는 그라디언트 생성 함수를 만들어, 클라이언트와 서버가 이 함수 하나를 같이 씀.
효과 · 같은 이벤트 이름은 언제 어디서 렌더해도 같은 티켓이 나옴.

04

카카오 로그인은 서버를 한 번 거쳐서

문제 · 사용 중인 인증 시스템에 Kakao 로그인이 기본 제공되지 않음. 한국 서비스에 카카오 로그인은 필수.
선택 · 서버에서 카카오 인증 코드를 받아 내부 인증 토큰으로 교환하는 방식을 직접 구현. 중간에 CSRF 방어 코드도 추가.
효과 · Google, Kakao, 익명 로그인 모두 같은 체계로 권한 관리가 가능해짐.

05

AI 도구로 반복 점검 루프 구성

문제 · 혼자 3주 안에 런칭하면서 한 사람의 눈으로는 놓치기 쉬운 부분이 생길 수 있음.
선택 · 기획·구현·코드 리뷰·한국어 UX 카피·경계면 일관성을 각각 AI에게 맡겨 여러 관점에서 코드를 다시 읽게 하는 루프를 구성.
효과 · 이터레이션 속도를 유지하면서 보완이 필요한 부분을 런칭 전에 정리할 수 있었음.

06 · TECH SUMMARY

사용한 기술, 짧게.

세부 스택보다 선택의 이유가 더 중요합니다. 한 코드베이스 안에서 웹 UI · 서버 API · 인증 · 서버 OG 이미지를 모두 다룰 수 있는 구성을 골랐습니다.

FRONTEND

모던 웹 UI 프레임워크로 PC와 모바일을 한 번에 대응. 애니메이션·컴포넌트·타이포까지 일관된 디자인 시스템을 유지.

EXTERNAL

카카오 로그인·공유, 장소 검색, 서버 OG 이미지 렌더링 등 한국 사용자 경험에 필요한 외부 서비스를 연동.

07 · LAUNCH SPRINT

3주, 3개의 마일스톤.

기획부터 런칭까지 3주. 각 스프린트마다 목표가 명확히 다르고, AI 제작 파이프라인이 모든 단계의 중심에 있었습니다.

SPRINT 1 · M1

MVP + AI 제작 파이프라인 구축

~ 2026-03-27

기본 기능이 돌아가는 MVP를 빠르게 만들고, 동시에 AI를 활용한 서비스 제작 파이프라인을 구축했습니다. 설계·코드 생성·리뷰·리팩토링 루프를 세팅해, 짧은 시간에 많은 기능을 만들 수 있는 환경을 확보하는 게 이 스프린트의 진짜 목표였습니다.

이벤트 생성·상세 RSVP 기본 흐름 Firebase 연동 기본 티켓 카드
SPRINT 2 · M2

브랜딩 + 실서비스화

~ 2026-04-03

단순 기능 중심의 MVP에 TIKIT의 브랜드 언어(티켓 메타포, 타이포, 그라디언트)를 입혔습니다. 제작 파이프라인을 한 번 더 강화해 이터레이션 속도를 끌어올렸고, 한 주 안에 여러 번 개선 루프를 돌릴 수 있게 됐습니다. 도메인(tikit.day)을 등록하고 실서비스 운영 준비도 이 단계에서 마쳤습니다.

브랜드 언어 적용 OG 이미지 서버 렌더 카카오톡 공유 최적화 도메인 등록 이터레이션 가속
SPRINT 3 · M3

QA + 보안 + UI/UX 보완 → GTM

~ 2026-04-08 런칭

PC·모바일 크로스 플랫폼 회귀 테스트와 엣지 케이스를 점검했습니다. AI 도구로 코드를 여러 차례 점검받아 런칭 전에 보완이 필요한 부분을 정리했고, 한국어 카피 리뷰와 인터랙션 회귀 테스트로 사용성을 마감했습니다. 4월 8일(수) 런칭 완료, 현재 운영 중입니다.

크로스 플랫폼 QA AI 코드 리뷰 한국어 UX 리뷰 런칭 · GTM
🤖

AI 활용 포인트

혼자 만드는 서비스에서 AI는 주로 반복 점검 용도로 활용했습니다. 3주라는 짧은 기간 안에 한 사람의 눈으로는 놓치기 쉬운 부분을 줄이는 데 도움이 됐습니다.

01 · 설계 리뷰

기능 스펙과 데이터 모델의 영향도를 사전에 분석. 나중에 스키마가 어긋나는 일을 예방.

02 · 구현 가속

반복 패턴 리팩토링과 보일러플레이트 생성. 손 품이 들어가는 단순 작업을 빠르게 처리.

03 · 코드 점검
