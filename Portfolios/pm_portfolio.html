Case 01 — FC Online

ea korea · 2025.01—11
▸ EA Korea · Development Manager, Client SE Part Lead

라이브 게임 리소스 플래닝 체계 개선

다수의 마일스톤이 병렬로 진행되는 환경에서 리소스 시뮬레이션 기반의 의사결정 체계를 정리했습니다.

~8명 Lead KR + CN release HLE / SvC
▸Situation
월 단위로 다수 마일스톤이 병렬 진행되는 대규모 라이브 게임. 각 마일스톤은 Pre-Planning → Production → Debugging → Hardening → Live의 단계를 거치며, KR·CN이 동시에 릴리즈되는 글로벌 운영 환경.
▸Task
  • 리소스 과부하를 사전에 감지할 정량적 도구 부재 — 스펙 범위 조정 시 "감"에 의존
  • 스펙 커팅 의사결정에 비교 가능한 시나리오 부재 — "줄여야 한다"는 합의는 있어도 "얼마나, 어떻게"의 근거 부족
▸Action
  • Milestone Gantt 재구성 — 각 마일스톤의 진행 단계를 날짜 축 위에 병렬 배치
  • 3-시나리오 비교 제안 — Full Spec / 일정 연장 / Spec Cut + 연장 (아래 참조)
  • HLE + SvC 대시보드 — Server/Client/Book 파트의 공수를 수치화, 인원 대비 소화 가능 여부를 "숫자"로 판단
  • KR/CN 릴리즈 조율 — 중국 측 POC(Release DD)와의 별도 채널로 우선순위 정리
▶ Custom Hub Release — Scenario Comparison spec × schedule × load
S1 Full Spec 기존 일정 초과
S2 Full Spec +2주 연장 정상
S3 Spec Cut +2주 연장 여유
▸Result
+ 스펙 커팅 논의가 시나리오 비교 기반으로 이동 — "줄여야 한다"에서 "S3로 가자"로 구체화
+ 마일스톤별 리소스 과부하 구간을 사전에 살펴볼 수 있게 됨
+ SvC 지표로 리소스 부담을 숫자 기반으로 공유

Case 02 — Project JSY

ncsoft · 2025.11—present
▸ NCSoft · 개발PM

대규모 스펙 로드맵 체계 설계

15개 파트 · 60+개 스펙의 로드맵과 팀별 부하를 하나의 문서에서 볼 수 있도록 설계했습니다. v1부터 v9까지 반복 개선해 실무에 정착시켰습니다.

15 Teams 60+ Specs v1 → v9
▸Situation
엔씨소프트의 신규 프로젝트 — 아트 · 기획 · 프로그램 등 여러 파트가 여러 개의 스펙을 동시에 진행하는 대규모 환경.
▸Task
  • 스펙의 팀·일정을 종합적으로 볼 수 있는 현황판 부재
  • 팀별 인력 배분이 적절한지 판단할 근거 부족 — 과부하/유휴 팀을 파악 불가
▸Action
  • 스펙 로드맵 반복 설계 (v1→v9) — 팀 요구사항을 누적 반영
  • 이슈트래커 연동 — 로드맵 스펙 → 사내 이슈트래커 일감 직접 링크. 거시(로드맵) ↔ 미시(태스크) 전환 가능
  • 3단 시트 구조 — 스펙 목록 · 로드맵 · 팀부하. 팀부하 시트는 월간 동시 진행 스펙 수 자동 집계 → "테트리스"식 일정 조정 가능

Case 03 — Project OS

콩스튜디오 · 2023.01—2025.01
▸ 콩스튜디오코리아 · Associate Production Director

신규 프로젝트 프로덕션 체계 + 게임 기획

Vertical Slice부터 프로덕션 방법론을 설계했고, 기획 인력이 부족했던 시기에는 UE5로 파쿠르 시스템·레벨·연출 프리비즈까지 직접 맡았습니다.

APD Waterfall + Agile UE5
▸Situation
신규 액션 어드벤처 프로젝트의 APD. Vertical Slice → Shipping 전체 로드맵을 세우고 실행해야 하는 단계. 소규모 팀 특성상 PM이 기획 영역까지 커버해야 하는 환경.
▸Task
  • 마일스톤 체계·프로덕션 방법론을 처음부터 정의
  • TMS 부재 → 일감의 위계·추적 체계 필요
  • 기획자 부재 상황에서 파쿠르 시스템 · 레벨 디자인을 직접 기획
▸Action
  • Hybrid (Waterfall + Agile) — 상위 계획 Waterfall / 실행 Agile로 분리
  • Airtable-based TMS — Objective → Epic → Task → Subtask 위계
  • 커뮤니케이션 체계 — Agenda 사전 공유 · 발산/수렴 정의 · Action Item 중심 · 회색 영역 식별
  • 게임 기획 직접 수행 — 파쿠르 시스템 상태 전이 다이어그램, 2h 필드 + 30m 던전 레벨, UE5 BP/카메라/시퀀서 프리비즈

▸Result
+ Vertical Slice 마일스톤 달성 — 기획 인력 공백기에 직접 기획·프로토타이핑을 맡아 첫 목표를 마감
+ Hybrid 방법론과 TMS 구조가 프로젝트 공통의 작업 체계로 자리잡음
+ PM 역할과 병행해 기획·레벨 디자인·연출까지 실제로 다뤄 본 사례가 됨

Case 04 — ZEPETO

naver z · 2022.06—2023.01
▸ NAVER Z · 콘텐츠 PM

IP 제휴 콘텐츠 WBS 표준화

20건 이상의 글로벌 IP(BTS · 현대자동차 · 나이키 등) 제휴 프로젝트를 위한 WBS 템플릿을 처음부터 정리했습니다.

20+ IPs Auto-schedule Partner comms
▸Situation
제페토 IP 제휴 아이템 제작 담당. 컨셉 → 원화 → 모델링 → QA → 릴리즈로 순차 진행되나 중간에서 전체 과정을 취합·정리하는 역할이 부재. 팀별 TMS가 달라 컨트롤타워 필수.
▸Task
  • 각 팀별 "어디까지 됐어요?" 반복 — 진행 파악에 매번 개별 확인 필요
  • 새 제휴 니즈마다 A-Z 스케줄링을 처음부터 다시 하는 비효율
▸Action
  • WBS 템플릿 설계 (처음부터) — 전체 프로세스를 5단계로 정의
  • 자동 일정 산정 — 릴리즈 타겟 날짜 입력 시 각 단계 시작일이 자동 역산. 월드 연계·영상 제작 여부 등 옵션별 분기
  • 제휴처 직접 소통 — 레퍼런스·라이선스 가이드라인·일정 조율을 사업팀 + 제휴처 동시 운영
▶ Stage Pipeline · auto-scheduled back from release concept → release
01 · Concept
컨셉 / 기획서 / 컨펌
시작일 자동 역산
02 · Art
스케치 → 1차 원화 → 컨펌
M/D 기반 일정 산정
03 · Model
3D → 리뷰 → 수정
실 작업일 자동 계산
04 · QA
기능 테스트 → 수정 → 최종
수동 할당
05 · Release
베타 등록 → 라이브
옵션별 분기
▸Result
+ "어디까지 됐어요?" 확인 커뮤니케이션을 줄임 — 진행률·일정을 같은 현황판에서 공유
+ 20+건의 제휴 프로젝트에 동일 템플릿 적용, 프로세스 안정화
+ 새 프로젝트 착수 시 스케줄링에 드는 시간이 줄어듦

Case 05 — TIKIT

personal · 0 → 1
▸ Personal · 기획 / 개발 / 브랜딩 / 운영 (1인)

PM이 직접 빌딩한 AI 서비스

코드를 직접 쓸 줄은 모르지만 AI 에이전트와 페어 프로그래밍으로 기획·개발·브랜딩·배포까지 혼자 진행한 0→1 경험입니다.

1-person M1 → M2 → M3 tikit.day ↗
▸Situation
"PM이 AI와 함께 실제 서비스를 어디까지 만들 수 있을까?"라는 질문에서 출발했습니다. 코드를 처음부터 쓸 줄은 모르지만 읽고 흐름을 따라갈 수 있는 수준의 이해도를 갖고 있었고, 부족한 부분은 AI와 협업으로 메워 보려 한 시도입니다.
▸Task
딱딱한 초대장 도구를 넘어, 일상의 모임을 소장하고 싶은 "티켓"으로 만드는 서비스. 마일스톤 목표: M1 PoC → M2 Brand → M3 GTM.
▸Action
▶ Milestone Chevron 3-step ship
M1 · PoC
기술 검증
  • AI 에이전트 페어 프로그래밍
  • 익명 유저 → 가입 마이그레이션 정책
  • 핵심 기능 기술 검증
M2 · Brand
브랜딩 + 파이프라인
  • TIKIT · Let's Tikit a day
  • v0 + Vercel + GitHub CI/CD
  • 1인 무제한 이터레이션 환경
M3 · GTM
운영 + PM 전과정
  • 백로그 / 우선순위 / 리스크 대응
  • 운영 정책 설계
  • 데이터 수집 구조 설계

상세 설계 결정과 AI 멀티에이전트 품질 검증은 TIKIT 케이스 스터디 ↗에서.

▸Result
+ tikit.day 런칭 완료, 링크드인 공유로 초기 피드백 수집
+ 프론트/백엔드 흐름과 렌더링·API 연동 구조를 실제로 따라가 보며 기술적 이해의 폭을 넓힘
+ 무엇을 만들지 결정하고 논리의 구멍을 찾는 역할은 여전히 PM의 몫이라는 점을 경험으로 확인
